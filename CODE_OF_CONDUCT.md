# Code of Conduct

## BylickiLabs Web Security Inspector

**Version:** 1.0  
**Effective date:** August 3, 2026  
**Project:** BylickiLabs Web Security Inspector 2.0.0  
**Responsible party:** Thorsten Bylicki | BylickiLabs  

---

## 1. Purpose of this Code of Conduct

BylickiLabs Web Security Inspector is a technical software project covering software development, web security, cybersecurity, data analysis, statistics, and systems integration.

This Code of Conduct defines the binding rules for respectful, professional, factual, and secure collaboration within the project. It applies to all persons interacting with the project, repository, communication channels, or associated development processes.

The objective is to maintain an environment in which technical discussions, bug reports, improvement proposals, security reports, and contributions can be handled constructively, transparently, and without personal attacks.

Participation in the project requires acceptance of this Code of Conduct.

---

## 2. Principles of Collaboration

All participants are expected to interact professionally.

This includes, in particular:

- respectful and factual communication
- clear and verifiable technical reasoning
- constructive criticism of code, documentation, and decisions
- separation of technical evaluation from personal judgment
- responsible handling of security-related information
- recognition of different levels of experience, backgrounds, and expertise
- willingness to correct mistakes and learn from feedback
- protection of confidential or non-public information
- compliance with applicable laws, policies, and platform rules
- transparent identification of personal contributions, changes, and sources

Technical disagreement is permitted and expressly encouraged, provided that it remains respectful, substantiated, and relevant to the project.

---

## 3. Expected Behavior

All participants are expected to:

- treat other people with respect
- answer questions factually
- express criticism specifically and constructively
- support technical claims with verifiable reasoning
- openly identify uncertainty or missing information
- provide reproducible information in bug reports
- handle security reports responsibly
- refrain from publishing confidential information
- consider existing decisions and project objectives
- review contributions before publication
- document code changes clearly
- credit the work of others correctly
- comply with copyrights and licenses
- avoid misleading statements about functionality or security
- assess automated analysis results professionally
- avoid intentionally minimizing or exaggerating risks

Criticism must address content, technical implementation, documentation, or process and must never target the personal characteristics of another participant.

---

## 4. Unacceptable Behavior

The following behavior is not accepted:

- insults, humiliation, or personal attacks
- threats, intimidation, or deliberate provocation
- discriminatory, racist, sexist, or hateful statements
- harassment in public or private communication
- publication of private or personal data without consent
- deliberate misrepresentation or manipulated evidence
- spam, trolling, or repeated off-topic contributions
- intentional disruption of discussions or development processes
- publication of confidential security information without coordination
- encouragement of unauthorized access or unlawful activity
- distribution of harmful content, malware, or destructive payloads
- misuse of the project against third-party or unauthorized systems
- circumvention of technical or organizational safeguards
- impersonation or acting in another person's name
- plagiarism or unauthorized use of third-party content
- false claims of official involvement in the project
- repeated disregard of moderation decisions
- retaliation against reporting or affected persons

Indirect, disguised, or supposedly humorous conduct may also be considered misconduct if it attacks or intimidates others or significantly interferes with collaboration.

---

## 5. Technical Discussions and Criticism

Technical discussions must be precise, verifiable, and solution-oriented.

Professional feedback should include, where possible:

- a clear description of the issue
- affected versions or components
- steps to reproduce
- expected behavior
- actual observed behavior
- relevant logs or error messages
- technical reasoning
- potential impact
- a concrete improvement proposal

Statements such as “does not work,” “is bad,” or “is insecure” are insufficient without verifiable technical information.

Strict technical criticism is permitted. Derogatory personal language is not.

---

## 6. Handling Security Reports

Security-related reports require particular care.

Security vulnerabilities, confidential technical details, or reproducible attack paths must not be published without review in public issues, discussions, comments, or social networks.

Reports should include:

- affected component
- affected version
- technical description
- reproduction requirements
- potential impact
- available evidence
- recommended mitigation
- assessment of urgency

Public exploit instructions, credentials, personal data, or sensitive system information must not be included.

Security reports must be submitted confidentially through an appropriate contact method of the project maintainer. The contact method listed on the BylickiLabs GitHub profile must be used.

Submitting a report does not create an entitlement to compensation, public recognition, prioritization, or implementation.

---

## 7. Responsible Use of the Project

BylickiLabs Web Security Inspector is intended for systems owned by the user, personal development environments, and explicitly authorized assessment targets.

All participants are personally responsible for:

- analyzing only authorized target systems
- obtaining all required approvals
- complying with legal and contractual requirements
- selecting an appropriate scope and system load
- protecting sensitive results
- treating exported reports confidentially
- manually reviewing automated results
- accounting for false positives and incomplete detection

The project must not be used to assess, disrupt, manipulate, or exploit third-party systems without authorization.

Contributions, requests, or discussions intended to facilitate abusive use may be closed or removed without further processing.

---

## 8. Scope

This Code of Conduct applies in all official and project-related areas, including:

- GitHub repository
- issues
- pull requests
- commit messages
- code reviews
- discussions
- releases
- project-related emails
- direct messages to project maintainers
- technical support requests
- social networks when communication occurs in the name of the project
- events or online meetings directly related to the project

It also applies to public behavior outside these areas when a person explicitly represents BylickiLabs or the project.

---

## 9. Reporting Violations

Violations of this Code of Conduct should not be discussed publicly if doing so could further endanger affected persons, confidential information, or ongoing reviews.

Reports should include, where possible:

- description of the incident
- date and time
- affected communication channel
- persons or accounts involved
- relevant links
- screenshots or other evidence
- potential immediate risks
- requested protective measures

Reports must be submitted confidentially to the project maintainer using the contact method listed on the BylickiLabs GitHub profile.

Knowingly false or manipulated reports are themselves a violation of this Code of Conduct.

---

## 10. Confidentiality and Data Protection

All reports will be handled confidentially to the extent reasonably possible.

Information will only be shared with persons required for review, moderation, technical processing, or legal evaluation.

The project maintainer will make reasonable efforts to:

- protect personal data
- avoid unnecessary disclosure
- store evidence securely
- avoid publicly exposing affected persons
- consider conflicts of interest
- review reports objectively and impartially

Complete anonymity cannot be guaranteed, particularly where legal obligations, platform rules, or necessary protective measures require disclosure.

---

## 11. Review and Handling of Reports

After a report is received, the following steps may be taken:

1. acknowledgment of receipt
2. review for completeness and plausibility
3. preservation of relevant evidence
4. assessment of potential risks
5. consultation with involved persons where appropriate
6. determination of temporary protective measures
7. decision on moderation or project measures
8. documentation of the result
9. communication with affected parties where possible

There is no entitlement to the publication of internal assessments, confidential evidence, or personal data.

---

## 12. Enforcement Measures

Depending on severity, frequency, intent, and impact, the following measures may be applied:

### Level 1: Notice

A private or public notice regarding inappropriate conduct and a request for correction.

### Level 2: Warning

A formal warning with clear expectations for future conduct.

### Level 3: Restriction

Temporary restriction from participating in discussions, issues, pull requests, or other project areas.

### Level 4: Removal

Closure or removal of contributions, comments, issues, pull requests, or other content.

### Level 5: Exclusion

Permanent exclusion from project areas where supported by the applicable platform.

### Level 6: Escalation

In serious, unlawful, or security-critical cases, information may be referred to platform operators, affected organizations, legal representatives, or competent authorities.

Measures may be combined or applied without prior escalation where the situation requires it.

---

## 13. Criteria for Moderation Decisions

When evaluating an incident, the following factors may be considered:

- nature and severity of the conduct
- actual or potential impact
- repetition of previous violations
- willingness to acknowledge and correct the behavior
- intentional or negligent conduct
- protection needs of affected persons
- security risks to the project or third parties
- confidentiality of the affected information
- legal or contractual obligations
- potential conflicts of interest

Moderation decisions are intended to protect the project, its participants, and technical collaboration.

---

## 14. Appeal and Reconsideration

Affected persons may request a factual reconsideration of a moderation decision.

An appeal should include:

- the decision concerned
- a verifiable explanation
- relevant new information
- possible misunderstandings
- a concrete proposal for resolution

Insulting, threatening, or repeatedly unsubstantiated appeals may be closed without further review.

The final decision remains with the project maintainer.

---

## 15. Responsibilities of Project Leadership

The project maintainer is responsible for interpreting and enforcing this Code of Conduct.

This includes:

- receiving reports
- reviewing violations objectively
- determining appropriate measures
- protecting confidential information
- disclosing conflicts of interest
- documenting moderation decisions transparently
- updating the Code of Conduct where necessary

Project leadership may reject, edit, hide, or remove content that violates this Code of Conduct, project objectives, applicable law, or platform rules.

---

## 16. Contributions and Intellectual Property

Contributors must ensure that submitted content may be used lawfully.

The following are not permitted:

- copied code without an appropriate license
- third-party documentation without authorization
- protected graphics or logos without usage rights
- confidential company code
- personal data
- credentials or API keys
- content from non-public sources
- contributions that infringe third-party rights

Acceptance of a contribution does not automatically create an entitlement to compensation, publication, attribution, or permanent inclusion in the project.

---

## 17. Automated Content and Artificial Intelligence

Contributions generated automatically or with the assistance of artificial intelligence must be fully reviewed before submission.

Contributors remain responsible for:

- technical correctness
- security
- license compliance
- data protection
- functionality
- quality
- traceability
- potential harmful effects

Unreviewed, misleading, or mass-generated automated contributions may be closed without processing.

---

## 18. Amendments to this Code of Conduct

This Code of Conduct may be amended if project scope, communication channels, legal requirements, or organizational conditions change.

Amendments will be published in the repository.

The current version applies from the stated publication date.
