## 1. Purpose of These Contribution Guidelines

These contribution guidelines describe how bug reports, improvement proposals, source code changes, documentation updates, tests, and security-related contributions may be submitted to BylickiLabs Web Security Inspector.

The objective is to maintain a clear, professional, and traceable development process.

Contributions should:

- be technically justified
- fit the project scope
- be documented transparently
- avoid unnecessarily affecting existing functionality
- consider application security and stability
- respect the bilingual structure of the project
- comply with the existing code and quality standards

Submitting a contribution does not create any entitlement to acceptance, publication, compensation, attribution, or permanent inclusion in the project.

---

## 2. Project Overview

BylickiLabs Web Security Inspector is a professional desktop application for the structured analysis of websites, domains, and web-based services.

The application includes, among other areas:

- HTTP and TLS analysis
- DNS and email security checks
- security headers
- cookie and CORS analysis
- form and content checks
- performance measurements
- risk and finding assessment
- statistics with NumPy and SciPy
- charts with Matplotlib
- local storage with SQLite
- exports to JSON, HTML, CSV, PDF, and SARIF
- German and English user interfaces
- automated build and quality assurance processes

Contributions must fit within this project context.

## 3. Requirements for Contributions

Before submitting a contribution, the following requirements should be met:

- the current repository state has been obtained
- existing issues and pull requests have been reviewed
- the change has been tested locally
- existing functionality has not been unintentionally altered
- new dependencies have been justified
- security implications have been considered
- German and English content has been kept synchronized
- code has been formatted and checked
- relevant tests have been executed
- documentation has been updated where necessary

Contributions without a clear description or sufficient validation may be rejected or closed.

## 4. Code of Conduct

All contributors must comply with the Code of Conduct published in the repository.

The following are expected in particular:

- respectful communication
- factual technical discussion
- constructive criticism
- responsible handling of security information
- no personal attacks
- no discriminatory or degrading content
- no publication of confidential data
- no abusive use of the project

Violations may result in the closure of issues or pull requests and exclusion from further participation.

## 6. Unwanted Contributions

The following contributions are not welcome:

- unauthorized attack or exploit functionality
- password attacks
- credential stuffing
- brute-force mechanisms
- destructive payloads
- malware
- ransomware functionality
- features intended to bypass access controls
- automated exploitation of third-party systems
- uncontrolled scanning of large target ranges
- hidden telemetry
- tracking without explicit consent
- collection of personal data
- unreviewed mass changes generated by artificial intelligence
- undocumented dependencies
- copied code without an appropriate license
- changes unrelated to the project
- deliberate weakening of existing security mechanisms
- removal of checks without a clear technical justification
- circumvention of target validation
- changes that may expose confidential data

Contributions focused on abusive or unlawful use will not be accepted.

## 7. Development Environment

### System Requirements

The following environment is recommended:

- Windows 10 or Windows 11
- Python 3.11 or newer
- Git
- at least 4 GB of memory
- internet access for dependencies and external APIs

### Clone the Repository

```bash
git clone https://github.com/bylickilabs/BylickiLabs-Web-Security-Inspector.git
cd BylickiLabs-Web-Security-Inspector
```

### Create a Virtual Environment

```powershell
py -3 -m venv .venv
```

### Install Development Dependencies

```bat
scripts\setup_dev.cmd
```

Alternatively:

```powershell
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
```

### Start the Application

```bat
START.bat
```

Alternatively:

```powershell
.\.venv\Scripts\python.exe main.py
```

## 8. Branch Strategy

Changes must not be developed directly on the main branch.

A separate branch must be created for each contribution.

Recommended naming conventions:

```text
feature/short-description
fix/short-description
security/short-description
docs/short-description
refactor/short-description
test/short-description
build/short-description
performance/short-description
```

Examples:

```text
feature/add-certificate-analysis
fix/sqlite-history-loading
performance/optimize-statistics
docs/update-installation
security/harden-url-validation
```

Branch names should:

- use lowercase letters
- use hyphens
- remain short and specific
- contain no special characters
- clearly indicate the purpose of the change

---

## 9. Commit Guidelines

Commits should be small, traceable, and focused on one subject.

Recommended prefixes:

```text
feat:
fix:
security:
docs:
refactor:
test:
build:
ci:
perf:
style:
chore:
```

Examples:

```text
feat: add extended TLS certificate analysis
fix: prevent duplicate scan history entries
security: harden target URL validation
docs: update Windows build instructions
perf: optimize SQLite history queries
test: add statistics regression tests
```

Commit messages should:

- be written in the imperative mood
- describe the actual content
- avoid generic statements such as “Update”
- not combine several unrelated changes
- contain no confidential information
- contain no credentials or API keys

Unsuitable examples:

```text
update
changes
fixed stuff
new version
test
work
```

## 10. Code Standards

Contributions must follow the existing Python style of the project.

### General Requirements

- Python 3.11 or newer
- readable and unambiguous identifiers
- clear separation of user interface, business logic, and data access
- type annotations where appropriate
- understandable error handling
- no unnecessary global state
- no hard-coded credentials
- no unnecessary side effects during import
- no uncontrolled network requests
- no blocking operations in the UI thread
- no unencrypted sensitive values in the source code
- no unnecessary dependencies
- no hidden background processes

### Code Documentation

New public classes, functions, and modules should contain understandable docstrings.

Docstrings should explain:

- purpose
- parameters
- return values
- possible exceptions
- security-related limitations
- side effects

Comments should explain why a solution is required rather than merely repeating what the code does.

---

## 11. Architectural Principles

Contributions must respect the modular architecture of the project.

The central areas are:

```text
app/core
app/scanners
app/reporting
app/ui
app/models.py
app/config.py
app/i18n.py
tests
```

### Scanner Modules

New checks should, where possible, be implemented as separate modules under `app/scanners`.

A scanner module should:

- have a clearly defined assessment purpose
- accept defined inputs
- return consistent finding models
- respect timeouts
- handle errors in a controlled manner
- avoid uncontrolled side effects
- make no destructive changes to the target system
- document results clearly
- be integrated into the central scanner
- be covered by automated tests

### User Interface

UI code should:

- avoid unnecessary mixing with scanner logic
- avoid long-running blocking operations
- use consistent terminology
- support German and English text
- respect existing layout and style rules
- present errors clearly
- avoid displaying sensitive data unnecessarily

### Database

Changes to the SQLite database must:

- consider backward compatibility
- account for migrations
- use transactions correctly
- process inputs through parameterized queries
- cover error cases
- avoid unintentionally deleting existing data
- be protected by tests

---

## 12. Internationalization

The application is fully bilingual.

All new visible text must therefore be provided in German and English.

This includes:

- buttons
- menus
- dialogs
- error messages
- status messages
- tooltips
- table headings
- finding descriptions
- settings
- report labels

No new function may be submitted if it is only fully usable in one language.

Translations must be technically correct, consistent, and equivalent in meaning.

Machine-generated translations must be reviewed manually before submission.

---

## 13. Tests

New features and bug fixes should be protected by automated tests.

At a minimum, the following should be tested where relevant:

- expected standard behavior
- relevant edge cases
- invalid input
- network errors
- timeouts
- database errors
- empty results
- invalid external responses
- safe handling of dynamic content
- existing backward compatibility

### Run Tests

```powershell
.\.venv\Scripts\python.exe -m pytest
```

### Run the Complete Quality Check

```bat
scripts\quality.cmd
```

The complete quality check includes:

- Python syntax validation
- compilation
- Ruff
- pytest
- core model tests
- scanner tests
- database tests
- statistics tests
- export tests
- input validation

A pull request should not contain known failing tests.

---

## 14. Code Analysis with Ruff

Ruff must be executed before submitting a pull request:

```powershell
.\.venv\Scripts\python.exe -m ruff check app tests main.py
```

Automatically fixable issues may be processed with:

```powershell
.\.venv\Scripts\python.exe -m ruff check --fix app tests main.py
```

Automatic corrections must be reviewed manually afterward.

---

## 15. Statistical Changes

Changes to NumPy, SciPy, or Matplotlib components require particular care.

The following are required:

- traceable mathematical justification
- a clear data basis
- defined handling of empty data series
- handling of NaN and infinite values
- stable results for small samples
- no misleading charts
- appropriate axes and labels
- reproducible tests
- documentation of new metrics

Statistical values must not influence the risk score without a technical justification.

---

## 16. Risk Model

Changes to the risk model must be documented and protected by tests.

A proposal must explain:

- which weighting is changed
- why the change is required
- which findings are affected
- how existing scans are changed
- whether historical comparisons are affected
- which thresholds apply
- how false positives are reduced
- which security implications exist

Unjustified score adjustments will not be accepted.

---

## 17. Export Functions

Changes to JSON, HTML, CSV, PDF, or SARIF exports must ensure that:

- special characters are processed correctly
- dynamic content is escaped safely
- no code injection is introduced
- internal data is not disclosed unintentionally
- existing fields remain compatible where possible
- file paths are handled securely
- exports do not write outside intended directories
- reports remain complete and readable
- new fields are documented
- output tests are included

HTML reports must not include unreviewed active content from target systems.

---

## 18. New Dependencies

New dependencies must be justified before introduction.

The justification should include:

- purpose of the library
- why existing components are insufficient
- license
- maintenance status
- security status
- size and build impact
- Windows compatibility
- impact on PyInstaller
- possible alternatives
- required changes to dependency files

Dependencies without clear value may be rejected.

Unmaintained, insecure, or legally unsuitable libraries will not be included.

---

## 19. Build and PyInstaller

Changes to the Windows build must remain compatible with the existing PyInstaller configuration.

Before submitting a pull request, run:

```bat
scripts\build_exe.cmd
```

The build must:

- work without manual post-processing
- include required resources
- exclude sensitive files
- display the correct version
- start without a separate Python installation
- exclude unnecessary development files
- be reproducible

Changes to the `.spec` file must be justified.

---

## 20. Documentation

Changes to functionality, installation, configuration, build, exports, or the user interface must be reflected in the main documentation.

Documentation should:

- be technically correct
- match the actual functionality
- avoid promising unavailable features
- contain understandable examples
- reproduce commands exactly
- cover German and English
- contain no confidential data
- avoid outdated screenshots or paths

Code changes without required documentation updates may be considered incomplete.

---

## 21. Creating Issues

Before creating an issue, check:

- whether a similar issue already exists
- whether the problem occurs in the current version
- whether the cause lies in a third-party component
- whether the issue is reproducible
- whether confidential security information is involved

A good issue includes:

- a meaningful title
- affected version
- operating system
- Python version
- installation method
- clear problem description
- reproduction steps
- expected behavior
- actual behavior
- relevant error messages
- sanitized logs
- screenshots where helpful
- possible cause
- possible solution

Issues with insufficient information may receive a request for details or be closed.

---

## 22. Feature Requests

Feature requests should explain:

- which problem should be solved
- which users are affected
- how the feature fits into the existing application
- which user interface area is affected
- which security implications exist
- which data will be processed
- which dependencies are required
- which alternatives were considered
- how the feature can be tested

A feature request is not a commitment to implementation.

---

## 23. Pull Requests

A pull request must:

- have a clear title
- reference an existing issue where applicable
- describe the purpose of the change
- explain technical decisions
- state effects on security and compatibility
- list completed tests
- include relevant screenshots where the interface was changed
- include documentation updates where required
- contain no credentials or sensitive data
- have a manageable scope

Large changes should be discussed in an issue first.

Independent changes belong in separate pull requests.

## 25. Review Process

Pull requests may be reviewed for:

- technical correctness
- security implications
- architectural compliance
- code quality
- test coverage
- performance
- usability
- translation quality
- database compatibility
- build compatibility
- documentation
- license compliance
- maintainability

Changes may be requested.

A pull request may be rejected if:

- it does not fit the project
- it introduces security risks
- tests are missing
- the change is not traceable
- existing functionality is unnecessarily affected
- dependencies are unacceptable
- license issues exist
- maintenance effort would be disproportionate

## 26. Merge Decision

The final decision on accepting, changing, postponing, or rejecting a contribution rests with the project maintainer.

A successful review does not guarantee a merge.

Contributions may be postponed if:

- a release is pending
- architectural changes are planned
- additional tests are required
- external dependencies remain unresolved
- security questions remain open
- priorities have changed

## 27. Security Vulnerabilities

Security vulnerabilities must not be submitted as public issues or pull requests.

They must be reported confidentially through the contact method listed on the BylickiLabs GitHub profile.

**GitHub profile:**

```text
https://github.com/bylickilabs
```

**Project repository:**

```text
https://github.com/bylickilabs/BylickiLabs-Web-Security-Inspector
```

A security report should include:

- affected version
- affected component
- technical description
- reproduction steps
- potential impact
- non-destructive proof of concept
- proposed mitigation
- preferred contact method

Public exploits, credentials, or confidential scan results must not be published.

---

## 28. Data Protection

Contributions must not contain personal or confidential data.

Before publication, remove in particular:

- names of uninvolved persons
- email addresses
- credentials
- API keys
- private keys
- internal hostnames
- internal IP addresses
- local user paths
- confidential target addresses
- complete response content
- non-public scan results

Screenshots and logs must be reviewed and sanitized before upload.

---

## 29. Intellectual Property and Licensing

By submitting a contribution, the contributor confirms that:

- they are authorized to submit it
- the contribution does not infringe third-party rights
- used content is appropriately licensed
- no confidential company data is included
- no third-party credentials are included
- the contribution may be used under the project license

Contributions must not be copied from third-party projects unless their license explicitly permits use.

Sources and licenses must be identified transparently.

Acceptance of a contribution does not create any entitlement to compensation or later control over the complete project.

---

## 30. Contributions Generated with Artificial Intelligence

Content generated with the assistance of artificial intelligence is not categorically excluded.

However, it must be fully reviewed.

The submitting person remains responsible for:

- technical correctness
- security
- quality
- license compliance
- data protection
- traceability
- functionality
- test coverage
- possible side effects

Unreviewed or mass-generated automated contributions will not be accepted.

---

## 31. Backward Compatibility

Changes should not unnecessarily break existing installations, stored scans, or exports.

For incompatible changes:

- reasons must be documented
- effects must be described
- migration paths must be considered
- version numbers must be updated
- database changes must be tested
- release notes must be prepared

Unannounced breaking changes will not be accepted.

---

## 32. Performance

Performance improvements must be measurable and traceable.

A contribution should include where possible:

- baseline state
- measurement method
- test environment
- comparison values
- result
- possible side effects

Optimizations must not disproportionately reduce readability, security, or maintainability.
